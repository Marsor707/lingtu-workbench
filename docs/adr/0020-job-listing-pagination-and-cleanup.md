# ADR 0020：任务列表分页 + 清理已完成任务 + 后台压缩数据库

## 状态

已采用

## 背景

ADR 0018 修掉了「启动时把整张任务表读进内存」的致命 OOM（`退出码 134`），但没有解决另一个事实：**任务库只会越来越大**。

- 编辑任务的源图以 base64 存在 `jobs.request_json` 的 `sourceImage` 里（单张上限 8MB，base64 约 10.7MB）；
- 结果图片落在 `workspace/jobs/<id>/` 下，一台长期使用的机器能积累几千个任务、上万张图；
- 出问题的用户库已经 GB 级：`launcher.log` 里迁移实体数据库花了 25 秒，随后启动即 OOM。

同时 `/api/jobs` 以前整表返回，前端把整个列表当唯一数据源：任务队列、筛选计数、搜索、画廊资产全从这一份数据算出。库一大，这条链路既慢又没法只取一部分。

## 决策

### 1. `GET /api/jobs` 改成分页 + 服务端筛选

- 参数：`page`（默认 1）、`pageSize`（默认 20，上限 100）、`status`、`search`；
- 返回 `{ items, total, page, pageSize, pageCount, counts }`，`counts` 是**全库**各状态计数（一次 `GROUP BY status`）；
- `page` 越界时**靠到最后一页**：清理后旧页码失效，不该给用户一张空白页；
- 新增 `jobs_created_at_idx (created_at DESC, id DESC)`：没有索引时翻页要把整表读一遍再排序（实测 1GB 库单页 119–389ms，建索引后 <1ms）。

### 2. 搜索交给服务端，但只搜低成本列

匹配 `id`、`mode`、`error_json`（编号 / 模式原值 / 错误原文），`%` 与 `_` 显式转义，避免用户输入把 `LIKE` 变成「匹配一切」。

**刻意不搜**提示词正文、布局、分辨率：它们在 `request_json` 这个大字段里，全库扫描实测 1GB 约 0.76 秒，10GB 库要 7–8 秒，搜一次卡一次。要补这块得先加一列小的 `search_text`（创建时写入 + 旧行后台回填），单独立项。

### 3. 清理已完成任务：`POST /api/jobs/cleanup`

- 请求体 `{ keepDays: 'all' | 7 | 30 | 90 }`；只接受这三个天数和「全部」；
- **只删 `status = 'completed'`**：运行中、排队、待复核、失败、已取消一律不动（失败的记录是排查线索，已取消是用户主动终止）；
- **不删图片文件**：用户明确选择「只删任务记录」。所以界面上必须写清楚「不会删除已生成的图片文件（图片仍占用工作区磁盘）」，否则用户会以为腾出了磁盘；
- 返回 `{ deleted, counts, vacuum }`，界面据此提示「已清理 N 个」并刷新列表与标签计数。

### 4. 压缩数据库放子进程，主服务不阻塞

`VACUUM` 会把整个库重写一遍（实测约 2 秒/GB，GB 级库要几十秒），而 `node:sqlite` 是同步 API，在主线程执行会冻住整个事件循环——页面所有请求、托盘 2 秒一次的健康检查全部卡住，看起来像服务挂了。

做法：

- 清理完成后**自动**安排压缩；压缩在子进程里跑（SEA 下 `spawn(process.execPath, ['--vacuum-db', db])`，开发态重跑本模块），主进程继续响应请求；
- 有排队/运行中任务时把压缩挂起（`pending`），每 15 秒检查一次，空闲后自己开始；
- 压缩结束由父进程执行 `PRAGMA wal_checkpoint(TRUNCATE)`：WAL 模式下不 checkpoint，回收的空间要等连接关闭才落到主库文件上，界面上看不到变小；
- 状态通过 `GET /api/maintenance` 暴露，界面轮询后把「正在后台压缩 / 已回收 X MB / 压缩失败原因」写在提示条里；
- 父进程退出时 `kill` 压缩子进程：否则它手里的独占锁会卡住下一次启动。

磁盘不足是 VACUUM 最常见的失败原因，子进程的 stderr 末尾会原样带进 `vacuum.error`。

### 5. 前端随之调整

- 任务队列自己分页取数（每页 20，上一页/下一页 + 第 N/M 页），筛选标签计数来自服务端；
- 搜索 300ms 防抖；筛选或搜索变化时回到第 1 页；
- 画廊不再从任务列表顺带取资产：改为按「已完成任务」分页拉取（「加载更多结果」），从队列点「查看结果」时直接读该任务；
- 清理按钮在「全部重试」旁边，按钮上直接写数量，清理动作在模态框里二次确认。

## 结果

- 浏览器实测（30 个已完成任务）：清理 → 列表 45 → 15，标签「已完成 0」；库文件 7.77MB → 2.94MB，提示条显示「已回收 4.7 MB」；图片文件仍在磁盘上（符合预期）。
- 后端 39 项测试通过，含真实子进程压缩、只删已完成、天数值校验、计数不受筛选影响、页码越界靠页、通配符转义。
- 代价与遗留：
  - 图片文件不随清理删除，工作区磁盘占用不会因为清理而下降。要回收图片得另做「删除图片」动作（不可逆，需要更强的确认），当前刻意不做；
  - 提示词/布局/分辨率不参与搜索；
  - `/api/stats` 仍扫全表两列，量级小，未改；
  - 源图仍以 base64 存在任务行里（ADR 0018 的后续项），根治要落盘成文件 + 旧数据迁移。
