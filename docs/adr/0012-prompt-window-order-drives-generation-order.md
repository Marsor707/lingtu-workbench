# ADR 0012：一裂多的提示词窗口顺序即生成顺序

## 状态

已采用

## 背景

一裂多的每个提示词窗口代表同一张源图的一个生成方向。在此之前，窗口列表没有排序能力：`.window-grip` 里的拖拽图标只是装饰，没有任何事件接线，窗口只能按「添加顺序」排列，也无法删除（原「删除窗口」按钮实际只清空正文并关闭开关）。

当方向变多（实际使用中常见 4 个以上），「哪个窗口是哪个方向」只能靠逐个读名称确认，误配方向的概率随窗口数上升。因此需要可调整的顺序。

关键约束是：窗口顺序在前端是数组顺序，在后端是执行顺序。`server/index.ts` 在任务开始时按 `windows.map(window => window.prompt)` 取提示词，逐个调用供应商，结果编号 `index = results.length` 与落盘名称 `${jobId}-${index+1}` 都由这个顺序决定。也就是说，调整窗口顺序会改变同一任务文件夹内的结果编号，并在生成画廊中改变图片排列顺序。

这使「排序」成为一个有实际后果的操作，而不是纯视图偏好，必须显式记录。

## 决策

- **窗口顺序即生成顺序**：前端数组顺序就是提交顺序，后端不做二次排序或归一化。
- **提供两条等价的排序路径**：`draggable` 拖拽（鼠标）与 `Alt + ↑/↓` 键盘排序。两者共用同一个「移动至目标下标」的函数，避免两套顺序逻辑分叉。
- **界面明示语义**：字段标题旁标注「生成顺序即窗口顺序」，窗口左侧显示 `01/02/…` 序号徽标，让顺序后果在操作前可见。
- **排序不改变任何已提交任务**，只影响之后创建的提交批次。
- 本次不改动原「删除窗口」按钮的既有行为（清空正文 + 停用），该按钮名不副实属于独立缺陷，另行处理。

## 结果

- 用户可以用鼠标或键盘把窗口调整到期望的生成顺序，结果编号与画廊顺序随之一致，方向与产出的对应关系可预期。
- 键盘路径是必需的替代方案：拖拽对键盘用户不可达，若只做拖拽，排序功能对这部分用户等同不存在。
- 代价：拖拽排序依赖 HTML5 原生拖放，合成鼠标事件无法触发 `dragover`，因此自动化验证必须走 `DataTransfer` + `DragEvent` 或 Playwright 原生 `dragTo`，不能用普通 mouse down/move/up 脚本代替。
- 代价：窗口顺序变化会改变结果编号，历史任务与新任务的编号规则一致但同名文件夹内不存在——编号只在一个任务文件夹内唯一，不跨文件夹。
- 代价：拖拽落点提示只做「插入到目标窗口之前/之后」的线性移动，不支持把多个窗口成组移动。方向数量足够多到需要成组操作时再评估。
