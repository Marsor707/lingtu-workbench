# ADR 0011：批量重试只覆盖失败任务，不接受已取消

## 状态

已采用

## 背景

任务重试长期只能逐个任务点击（见 ADR 0003）。当供应商接口抖动或密钥失效时，队列里会一次性堆积大量失败任务，逐个点击不现实，因此需要"全部重试"。

问题在于准入条件。单个任务的重试对失败和已取消都开放，理由是两者都代表"这一轮没有拿到结果，而原请求参数还在"——已取消往往是用户自己中断后想换个供应商再跑一次，语义上确实需要重试。

但队列里还有第三种非成功终态「待复核」，它代表供应商可能已经计费、结果需要用人工确认，批量重跑会直接放大重复计费风险。已取消虽然风险低，含义却完全不同：它是用户主动终止，之后很可能已经新建了替代任务，批量重跑会把用户明确放弃过的工作重新付费执行一遍。

## 决策

- **批量重试的准入条件只有 `failed`**：`POST /api/jobs/retry-failed` 由服务端自行筛出所有失败任务并逐一走既有的任务重试路径，不接受前端传入任务 ID 列表。
- **单任务重试的准入保持不变**：`POST /api/jobs/:id/retry` 仍同时接受 `failed` 与 `cancelled`。
- **待复核不进入任何重试入口**：批量与单个重试都保持排除，维持"可能已计费，需人工确认"的原意。
- **批量重试是页面级操作**：不受筛选页签与搜索条件影响，按钮上直接给出失败任务数量，点击前经一次原生确认提示。

## 结果

- 单个重试与批量重试存在有意的不对称：某条已取消任务能被单独重试，却不会被"全部重试"带上。这是刻意的，不是遗漏；用户想要它回来，逐个点即可。
- 用户不会因为一次误点而把历史上主动放弃的任务全部付费重跑一遍，批量操作的风险面被限制在"确实失败过"的任务上。
- 代价：如果用户确实想批量重跑已取消任务，当前没有入口。需要时再评估，而不是现在先做一个更宽的范围。
- 代价：目标集合由服务端判定，前端只能拿到"实际重试了几个"，无法预先知道自己那一次点击的确切影响；数量提示因此需要在点击前由前端从队列投影里算出，两者不一致时按"状态已变化"提示。
