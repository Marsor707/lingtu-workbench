# ADR 0019：数据目录可配置，默认仍在用户数据目录

## 状态

已采用

## 背景

1.0.10 把用户数据从安装目录搬到 `%LOCALAPPDATA%\lingtu-workbench-data`（ADR 0017），解决了"重装到新文件夹必丢数据"。但 1.0.11 上线后用户第一反应是"生图任务成功了，图却没落到 workspace/jobs 目录下"——他去的是旧安装目录 `E:\工具\LT\灵图工作台\workspace\jobs`。

两类真实诉求：

- 用户习惯于"图片跟着程序放"，尤其是装在 `E:` 这种大容量盘、系统盘紧张的场景；
- 数据目录现在整体在 `C:`，而 `lingtu.db` 因为把编辑源图以 base64 存在 `jobs.request_json` 里（见 ADR 0018），已经 6–10GB，图片本身又是几十 GB 量级。

同时，把默认目录改回 `$INSTDIR` 有三个硬问题：

1. NSIS 卸载/换文件夹重装会 `RmDir /r $INSTDIR`，图片连库一起没；
2. 装在 `C:\Program Files` 时普通用户进程对 `$INSTDIR` 没有写权限，生图直接失败；
3. 数据跟着安装盘跑，安装盘一换，历史任务里的图片全变死链。

## 决策

- **默认仍是 `%LOCALAPPDATA%\lingtu-workbench-data`**，但托盘新增「更换数据目录…」，用户可把**数据库 + workspace 一起**搬到任意目录（典型是 `E:\灵图数据`）。
- **数据库必须一起搬**：占空间的大头是 `lingtu.db`（源图 base64），只搬图片等于没解决空间问题；而且"一个根目录"意味着一条路径解析、一次迁移、一个「打开数据目录」入口。等 ADR 0018 的后续改造（源图落盘成文件）让库瘦下来之后，再谈拆分才有意义。
- **选择结果记在 `%LOCALAPPDATA%\lingtu-workbench-data-root.txt`**：指针必须在"数据目录自身之外、又不在卸载器删除范围内"。这样即使用户卸载时勾了「删除应用数据」，指针和 `E:` 上的数据都还在，重装后直接续用。
- **指针指向的目录不存在时明确报错，不静默退回默认目录**：默认目录里可能是切目录之前的旧快照，静默使用会表现为"提示词和图片全退回去了"，比报错可怕得多。托盘会显示"上次选择的数据目录不存在：<路径>……请用托盘菜单「更换数据目录…」重新选择"，而这个菜单项在这种状态下依然可用——否则用户就锁死在打不开的工作台里。
- **切换流程固定为：停服务 → 复制 → 记指针 → 重启**。停服务是因为运行中的进程在写 WAL，此刻复制会拿到坏快照；复制只做非覆盖式合并，目标已有 `lingtu.db` 时直接使用（用户可能是在切回旧目录）；任何一步失败都把服务拉回旧目录，并弹出说明，绝不留"服务停了但目录没换成"的状态。
- **复制期间托盘显示进度语义**：`ServicePhase::Restarting` 支持携带 `detail`，文案为"正在更换数据目录，复制数据到 <路径>…"，同时禁用两个可点项。GB 级复制可能持续几分钟，没有这句用户会以为程序卡死。
- 引入 `tauri-plugin-dialog`（新增依赖的唯一来源）：需要系统原生"选择文件夹"对话框，浏览器里没有等价能力，而服务端（HTTP sidecar）无法弹原生对话框。

## 结果

- 用户可以把数据放到任意本地盘，`C:` 不再被几十 GB 图片和几个 GB 的库占满；默认行为对普通用户仍然是安全的。
- 数据位置在托盘里可查（「打开数据目录」每次现算，不缓存）、柜面可换、日志里可见（`launcher.log` 的"数据目录="与 `execution.log` 的 `service_started.workspaceDir`）。
- 代价与风险：
  - 用户可能把数据选到移动硬盘或网络盘上。拔盘后应用会明确报"数据目录不存在"而不是悄悄换库；SQLite 在 SMB 上的锁语义不可靠，文档里只说"建议本地固定盘"，没有强制拦截。
  - 复制不做进度条，只有托盘文案与日志耗时；超大库（>10GB）切换到另一个物理盘会明显慢。
  - 切换后旧目录保留原样（只复制不删除），用户需要自己清理，文档里已写明。
- 未覆盖：不支持"数据库留本地、图片放别的盘"的分裂配置。需要它的前提是库先瘦下来（ADR 0018 后续项）。
